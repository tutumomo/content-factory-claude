# 只給主題、由智能體生成完整小說：可行性評估

日期：2026-11-25
狀態：**評估，未實作**
相關：`docs/DESIGN-NSFW-20261124.md`（分級與模式）、`app/prompts.py`、`app/pipeline.py`

## 結論

**可行，但「一次生成整本」與「分段生成再組裝」是兩種完全不同的東西，只有後者能成立。**

實測數據：本機 `inkling-2-mini-abliterated-fit` 產出 3 段、共 487 字的小說片段，花了 **96.5 秒**。

由此推算：

| 目標篇幅 | 段數（每段約 160 字） | 預估時間 | 一次呼叫可行？ |
|---|---|---|---|
| 極短篇 500 字 | 3 | ~1.6 分鐘 | 勉強 |
| 短篇 3,000 字 | 19 | ~10 分鐘 | 不行 |
| 中篇 15,000 字 | 94 | ~50 分鐘 | 不行 |
| 長篇 60,000 字 | 375 | ~3.3 小時 | 不行 |

一次呼叫的天花板不只是時間，還有**輸出長度上限**。本機模型與多數 API 的單次輸出約 4k–8k token（中文約 3,000–6,000 字），硬要它寫一萬字只會得到被截斷的 JSON，然後整段失敗。

所以設計必須是**分章生成、逐章累積**。

## 為什麼現有架構已經能吃下大半

好消息是骨架已經在了。目前一集的資料流是：

```
brief（方向）→ script（scenes[]）→ critique（多角色審稿）→ storyboard → assemble
```

`scenes[]` 就是天然的「段落」單位。小說的每一章可以對應一個 scene，`narration` 放正文。也就是說：

- **模式**：`fiction`（上一輪已加）
- **形態**：`novel` / `serial`（上一輪已加，輸出 `novel.txt` / `serial.txt`）
- **不查證**：`UNVERIFIED_MODES` 已讓 fiction 跳過來源閘門
- **審稿角色**：文字形態已有「文字質地／情節連貫／閱讀推力」

缺的是三件：

1. **生成長度不受 `fmt_desc` 限制**（現在寫死「短片 150–300 字」「長片 900–2000 字」）
2. **分段續寫**（第二章要讀得到第一章，不然人物與設定會漂）
3. **字數與章節的目標設定**（使用者要能說「寫一萬字、十二 chapter」）

## 建議的設計

### 1. 新增目標設定（不是新的 `form`，而是 `form=serial` 的參數）

```
ep["target"] = {"chars": 10000, "chapters": 12, "pace": "slow"}
```

`form=novel` 指短篇（單次可完成），`form=serial` 指連載（必須分段）。分界線建議 4,000 字：超過就自動轉 `serial`。

### 2. 分章生成的骨架

不要一次要模型寫完，改成**三段式**：

```
大綱（一次呼叫，便宜）
  ↓  {"title","logline","cast":[{"name","role","want","voice"}],"chapters":[{"no","beat","pov"}]}
逐章生成（每章一次呼叫）
  ↓  帶入：大綱 + 前情摘要（不是前文全文）+ 這一章的 beat
累積 → 章節檔 → 合併
```

**關鍵是「前情摘要」而不是「前文全文」。** 把前面所有章節貼回去，第 10 章就會撞到上下文上限；貼一份 300 字的滾動摘要，成本固定，而且逼模型自己記住重點。

### 3. 一致性靠三件事，不靠模型記性

長篇最容易壞的是「同一個角色換了名字、換了性格」。三個便宜的做法：

| 做法 | 做法 | 成本 |
|---|---|---|
| 角色聖經 | 大綱階段抽出角色卡（名字、慾望、說話方式、口頭禪），每章貼回去 | 一次生成，每章幾百字 |
| 滾動摘要 | 每章寫完，用同一模型壓成 200–300 字摘要，餵給下一章 | 每章多一次小呼叫 |
| 章末檢查 | 每章寫完比對角色聖經，名字或性格不一致就重寫該章 | 每章一次判定 |

角色卡可以直接沿用既有的 `app/characters.py`——它已經有 `name`、`description`、`seed_base`，只要加 `voice`（給廣播劇用）與 `speech`（說話習慣）兩個欄位。

### 4. 進度與中斷

一章 30–60 秒，十二 chapter 就是 6–12 分鐘。這不能卡在一個 HTTP 請求裡：

- 每章寫完就落盤（`output/chapters/ch01.json`），中斷可續
- 走既有的 worker 佇列，一個 job 一章（或一批三章），狀態寫進 `episode.json`
- 前端顯示「第 4/12 章，已完成 3,200 字」

### 5. 品質閘門要調整

現有的審稿是「四個角色各打一次分、低於 8 分修稿」，對長篇不適用：一章 8 分不代表整本好。建議改成：

- **每章**：只跑「文字質地」與「情節連貫」兩個角色
- **每三章**：跑一次「閱讀推力」，檢查節奏有沒有拖
- **全書完成後**：一次總審，看開頭鉤子、中段轉折、結尾收束

## 兩個要小心的坑

**第一，`_validate_script()` 會把空 narration 的段落濾掉。** 如果模型某章寫空，那一章會安靜消失，章號就錯位。長篇生成必須用新的驗證：章節數要對得上，缺章就重試那一章，不能略過。

**第二，`fmt_desc()` 的字數上限會誤導模型。** 現在不管什麼形態都說「短片 150–300 字」。`form=serial` 時要改成逐章的目標字數，否則模型會寫成 300 字的極短篇。

## 建議的實作順序

1. **目標設定與字數控制**（半天）：`ep["target"]`、`fmt_desc` 依形態給字數、`_validate_script` 增加章節完整性檢查
2. **大綱階段**（一天）：新的 `st_outline`，產出大綱與角色卡，寫進 `output/outline.json`；這是唯一需要人工看一次的地方
3. **逐章生成**（一天半）：`st_chapters`，滾動摘要、可續傳、每章落盤
4. **總審與合併**（半天）：全書審稿、合併成單一 txt／md

合計約 3.5 天，不含調 prompt。

## 與廣播劇產線的關係

這兩件事可以疊在一起，順序建議是**先有小說、再做廣播劇**：

- 小說階段產生角色卡（含 `voice` 與 `speech`）
- 廣播劇階段把每章拆成「旁白／角色對白」，用角色卡上的音色設定逐句合成

如果先做廣播劇，會被迫在沒有完整文本的情況下猜角色；先有小說，角色設定是現成的。

## 未驗證

- 96.5 秒是「3 段 487 字」的單次呼叫，章節更長時是否線性增長未測。
- 滾動摘要是否能真的防止人物漂移，需要實際寫完一本 12 章才能確認。
- 本機模型寫長篇中文的連貫性沒有樣本；建議第一次先跑 6 章、3,000 字，確認品質再放大。
